# v1.4.1 — the macOS submenu actually converts

If you're on macOS and the right-click **File Converter** submenu listed all
your presets and then did nothing when you clicked one, this release is for
you. The menu was never broken; the click was. Every macOS install of v1.4.0
had this, which is why the fallback Quick Action was the only thing that
worked.

Linux gets one small menu-label fix and is otherwise untouched.

## The click went nowhere

A Finder Sync menu doesn't stay in the extension. Finder rebuilds it in its own
process, and what comes back on a click is a *new* `NSMenuItem` — so the preset
name, which travelled in `representedObject`, arrived empty. The selection had
the same problem: asking `FIFinderSyncController` for it again at click time
can answer with nothing.

Both cases hit a `guard ... else { return }`. No error, no log, no dialog. The
submenu looked completely alive and converted nothing, ever.

Now the preset travels as the menu item's integer `tag`, and the selection is
captured when the menu is built. The tags are 1-based on purpose: a tag that
doesn't survive reads as `0`, and `0` must not quietly select the first preset —
converting with the wrong preset is worse than not converting. Both failure
paths log to the console instead of returning in silence.

## Why a conversion could look frozen

The submenu hands your files to `File Converter.app`, which opens them from an
ordinary child process. That means macOS asks for permission — once per
protected folder (Desktop, Documents, Downloads, external drives), in File
Converter's name.

An unanswered prompt doesn't fail the conversion, it *parks* it: ffmpeg and
ImageMagick block inside `open()` until someone answers, and the progress
window sits there looking hung. In v1.4.0 that prompt also arrived with no
explanation, because the app carried no usage-description strings.

This release adds them, so the prompt says what it wants and why. The installer
now says the same thing at the end of setup, and the README explains how to
skip the prompts entirely by adding **File Converter.app** (it lives in
`~/Applications`, not `/Applications`) to System Settings → Privacy & Security →
Full Disk Access.

Quick Actions were never affected: they run inside Apple's Services runner,
which already holds the access. That difference is exactly why the submenu
looked broken while the Quick Action worked.

## One menu instead of two

When the Finder submenu is live, the generic **File Converter…** Quick Action is
no longer installed. It offered, one level deeper, what the top-level menu
already offers. It's still the fallback when the submenu isn't available — no
Swift toolchain, extension not enabled — so nobody ends up with no menu at all.

## Reinstalling stops re-signing the app

`File Converter.app` is ad-hoc signed and was rebuilt from scratch on every
install, which handed macOS a different binary each time and made it re-register
the extension for no reason. The installer now stamps the build (a hash of the
Swift sources, the version and both Info.plists) and keeps the existing binaries
when nothing changed.

## Linux

Menus that can't nest — Nemo actions and Dolphin's single-level service submenu
— now label a foldered preset `Scale 720p → To Mp4` instead of showing several
identical `To Mp4` entries.

## Upgrading

Re-run `./install.sh`. On macOS it rebuilds the Finder extension with the fix;
your presets and settings are untouched.
